# Решения

Формат: дата — решение — почему.

## 2026-10-05

- **Разработка на самом Mac mini, в `~/Desktop/Zelenogorie`.** Прод будет жить в `~/srv/zelenogorye/releases/<время>` с симлинком `current` (этап 1б, 7). Desktop для прода не годится из-за ограничений доступа macOS (TCC) для launchd.
- **Dev и прод разделены.** Dev: порт 3001, база `data/dev.sqlite`, env `~/.config/zelenogorye/.env.development`. Прод: порт 3000, env `~/.config/zelenogorye/.env`.
- **Node 24 из nvm** (`~/.nvm/versions/node/v24.13.1`), а не из Homebrew. В plist этапа 1б путь к node указывать абсолютный, из `which node`.
- **Сервер собирается esbuild в `server/dist`**, зависимости остаются внешними, `@zg/shared` вшивается. Dev — `tsx watch`.
- **Один BUILD_ID на сервер и клиент** (`scripts/build.mjs`). Клиент шлёт его в `sync:hello`; при несовпадении перезагружается один раз на версию.
- **Вход.** Приглашение гасится только POST-запросом по кнопке; GET безопасен для превью-ботов. Игрок задаёт 6-значный PIN при входе по приглашению. Вход по коду комнаты: выбор участника из списка (имена игроков и мастера видны тому, кто знает код комнаты; стол в списке не показывается) + PIN или пароль.
- **Rate limit.** 5 неудачных попыток за 15 минут на участника + 50 любых попыток за 15 минут на IP. В памяти процесса, после перезапуска сбрасывается. Следствие: кто знает код комнаты, может временно заблокировать вход конкретному игроку пятью неверными PIN — для домашней игры приемлемо.
- **Мастер входит паролем** (от 8 символов), он задаётся в `npm run setup`. У стола секрета нет: стол входит только по приглашению, мастер может выдать новую ссылку.
- **Предохранитель утечек** (`server/src/visibility/guard.ts`) блокирует ответ не-мастеру, если в нём маркер `СЕКРЕТ-МАСТЕРА` или ключи `gm_*`, `*_gm`, `gmXxx`, `xxxGm`. Следствие для кода: в DTO игрока и стола нельзя называть поля так, даже безобидные.
- **Jev.** SDK `@typesafe-ai/sdk` 0.6.0: параметры клиента `defaultModel` и `retry` (а не `model`/`retries`). Модель закреплена `jev-1.13.0`. `logLevel: 'warn'`, потому что `debug` печатает тела запросов с мастерскими текстами.
- **Мастерские тексты и черты уходят во внешний API TypeSafe** (как и в Claude API). Записи дневника «только для меня» не уходят никуда.
- **Определение зелёной магии для Jev** (`server/src/ai/jev/questions/greenMagic.ts`) взято из канона рандомизатора: чудеса, исполняющие желания (Lesser Miracle, Miracle, Divine Miracle), перегрузка — глаза и изумрудная кожа. Отсечение «мана, молитвы, способности родного мира — не зелёная магия» — моё прочтение канона, проверить. В песочнице определение можно править на лету.
- **Известное ограничение:** если дома пропал интернет, игра встаёт и для сидящих за столом — весь трафик идёт через Cloudflare.

## 2026-10-05, этап 2

- **Рандомизатор:** взята живая версия артефакта «Переход в Зеленогорье» с claude.ai (обновлена 2026-10-04), сохранена как `reference/randomizer-v5.17.html`. Внутри артефакта номер версии не записан (комментарии упоминают v5.10–v5.13).
- **Справочники остаются JSON-файлами в `seed/`**, а не таблицами в базе. Их делает `tools/extract-seed/extract.mjs`: куски данных выполняются в изолированном `vm`, строки попадают в JSON без изменений. Сервер читает их при старте и проверяет форму через Zod. Причина: движок работает с порядком строк как с частью логики (от него зависит выбор генератора), а таблицы в базе этот порядок не гарантируют.
- **`npm run seed` создаёт тестовых персонажей**, а не справочники.
- **Персонаж хранится как документ Char рандомизатора** в `character_secret.doc` (JSON) плюс строка `character` (комната, владелец, вид, имя, описание для игрока). Отдельной таблицы `trait_assignment` нет: слоты, ступени, раскрытие и история живут в документе, как в артефакте. Так импорт и экспорт JSON идут без потерь, а движок переносится без переписывания.
- **Движок перенесён построчно** (`server/src/domain/`): генератор (FNV-1a + mulberry32), индекс черт, бросок, сродство с профессией и архетипом, переброс, ручной выбор, доп. слоты, карточки, ступени, развилки, слои «Для мастера», уровень силы. Порядок вызовов генератора не менялся: тот же сид даёт того же персонажа.
- **Раскрытие** как в артефакте: `revealed = {trait, stages, price, hint}`. Добавлен режим «только подсказка»: черта не раскрыта, но подсказка задана — игрок видит текст подсказки без названия и категории. Уровни для мастера: скрыта / подсказка / раскрыта.
- **`projectForPlayer`** — перенос `toPublic` с белым списком полей и `PlayerCharacterSchema.parse` (strictObject на всех уровнях). Слоты без раскрытия и без подсказки не оставляют ничего. У слотов в ответе игроку нет идентификаторов.
- **Действия мастера с чертами** идут через Socket.IO (`gm:trait.setReveal`, `setStage`, `setTier`, `setFork`), остальное (бросок, сохранение, импорт, мета) — HTTP. Первая строка каждого `gm:*` — проверка роли.
- **У одного игрока — один персонаж.** Попытка отдать второго — ошибка `owner_taken`.
- **Местный персонаж** пока минимальный: имя, обращение, описание для игрока, заметки мастера, уровень силы. Что ещё нужно в его карточке — открытый вопрос.
- **Правило разницы сил в артефакте уже есть** (`powerCompare`): сравниваются ступени силы (Обычный, Героический, Монструозный, Легендарный, Полубог, Божественный), а не отношение чисел. Противник на две ступени выше — крит лишь царапает; на две ниже — критический урон без крита. Это расходится со стартовым предложением этапа 3 (отношение r). Решить до этапа 3.
- **Рекомендуемый уровень силы для ступеней** из артефакта: Освоение от 50, Мастерство от 100, Предел от 300. Показывается мастеру как подсказка, ничего не блокирует.

## 2026-10-05, этап 3

- **Правило разницы сил — из канона рандомизатора (`powerCompare`), не из стартового предложения плана.** Сравниваются ступени силы: Обычный 1–50, Героический 51–100, Монструозный 101–300, Легендарный 301–600, Полубог 601–1000, Божественный 1001+. Противник на 2+ ступени выше: любой успех d10 становится «Лишь царапина». На 2+ ступени ниже: успех → «Критический урон», провал → «Заметный урон». Разница в одну ступень — обычный бросок. T3.1 и T3.2 из плана этому правилу соответствуют. **Требует подтверждения Рустема** (`server/src/domain/rolls.ts`, одна функция).
- **Таблица d10** — стартовое предложение плана: 1 провал с осложнением, 2–5 провал, 6–8 успех, 9 сильный успех, 10 крит. d20 — бросок удачи без учёта силы.
- **Сила противника задаётся мастером на сессию** («Сессия» → «Противник»), а не в каждом броске. Игрокам ни имя, ни сила противника не уходят. Броски мастера идут без поправки на силу.
- **Лента: одна строка события на аудиторию** (`public`, `table`, `gm`, `member:<id>`) со своим `seq`. В строке лежит уже спроецированный DTO этой аудитории: игроку — публичный, мастеру — полный. Клиент хранит `lastSeq` по своим аудиториям; пропуск номера — сигнал досинхронизироваться (`sync:hello`). При сильном отставании или «будущем» номере (база восстановлена) приходит снимок последних 50 по всем аудиториям.
- **Дедупликация бросков** по `(member, clientRequestId)`: «Повторить» отправляет тот же id, двойное нажатие заблокировано на клиенте.
- **Все обработчики Socket.IO обёрнуты в try/catch** (`realtime/guarded.ts`): исключение — в лог и ответ `server_error`, процесс не падает. Повод: предохранитель утечек бросает исключение, и игрок мог бы уронить сервер, вписав маркер в текст броска. Такой текст теперь отклоняется на входе.
- **Jev в бросках (rollIntent, greenMagic) пока не подключён**: по плану — только после решения по итогам J0.

## 2026-10-05, этап 4

- **Экран мастера разбит на разделы:** «Игра» (противник, бросок, лента), «Партия» (персонажи, перегрузка), «Запросы» (дневники и вопросы игроков), «Заметки», «Участники» (приглашения, песочница Jev).
- **Перегрузка зелёной магией** — отдельная таблица `green_overload`: значение и пороги «глаза» (3) и «кожа» (6) на персонажа. Наружу уходит только по кнопке «Показать столу» и только видимый признак (`table:sign`), без числа.
- **Дневник:** три вида записи — обычная (видит мастер), «только для меня» (мастер не видит ни в UI, ни через API; фильтр в SQL-запросе, `diaryForGm` бросает исключение на личной записи), «вопрос мастеру» (не может быть личным, у мастера — со статусом «ждёт ответа / отвечен»).
- **Заметки сессии** — на текущую игровую сессию, автосохранение через 0,8 с после последней правки. Сохранение проверяет `updatedAt` версии, от которой шла правка: если в другой вкладке сохранили позже, мастер выбирает версию, ничего не затирается молча.
- **Jev подключён за флагами** `JEV_LEAK_GUARD`, `JEV_DIARY_MATCH`, `JEV_GREEN_MAGIC` (`rollIntent` пока нет). Пороги — стартовые, в `server/src/ai/jev/thresholds.ts`: страж 0,5 (чужая черта) и 3 из 4 (своя), дневник 2 из 3, зелёная магия 0,5. Уточнить по итогам J0. В проде флаги по умолчанию выключены (`config.ts`), в `.env.development` — включены.
- **Страж срабатывает до сохранения подсказки** (`/hint-check`), а не после: мастер видит предупреждение и решает сам. Если Jev не ответил — «проверка недоступна», сохранить можно.
- **Ответы Jev хранятся в `ai_judgment`** (мастерские данные). Подсказки «зелёная магия?» живут только в открытой вкладке мастера; после перезагрузки вкладки они пропадают (сырые ответы остаются в базе).

## 2026-10-05, этап 5

- **Сцена** — таблица `scene` (название, текст для стола, `text_gm`, картинка). Что показано на столе — `table_state`. Столу уходит только `projectForTable` (strictObject), `text_gm` не читается.
- **Картинки сцен** проходят через sharp: EXIF-поворот, не больше 1920 px по длинной стороне, WebP качества 80, метаданные выброшены. Лежат в `data/media/` (рядом с базой, вне релизов), имя файла случайное. Отдаются через `/api/media/…` с проверкой: мастеру — любая картинка его комнаты, столу — только картинка показанной сейчас сцены, игрокам — ничего. Кэш `private, immutable`: у каждой загрузки новое имя. Бэкап на этапе 7 должен забирать и `data/media/`.
- **Загрузка картинки** — сырым телом запроса с `Content-Type: image/*`, до 15 МБ, без multipart. HEIC зависит от сборки libvips в sharp; iPhone при выборе фото в браузере обычно отдаёт JPEG.
- **Стол** — отдельный полноэкранный экран без кнопки «Выйти»: сцена, последние 5 публичных бросков, плашки признаков перегрузки на 12 с. «Анимация выкл.» хранится на самом устройстве стола.
- **Страж Jev для текста сцены** проверяет по скрытым и намекнутым чертам всех персонажей комнаты (до 40 черт за запрос) перед «Показать на столе».

## 2026-10-05, этап 6

- **Сводки — перенос «SUMMARY» из рандомизатора:** три вида (для мастера, вступление для игрока, сцена перехода), промпты, пример, тоны и лица — дословно из `seed/summary-*.json`. Данные: мастеру — всё, включая заметки (урезка до 12 000 символов как в артефакте); вступлению — только `projectForPlayer` в форме `toPublic`, без подсказок к нераскрытым чертам; сцене перехода — происхождение и «признаки до раскрытия» скрытых черт.
- **Модели:** «Написать» — `claude-sonnet-5-5` (effort `medium`, мышление адаптивное по умолчанию, серверный запасной вариант при отказе — `fallbacks: 'default'`), «Быстрый черновик» — `claude-haiku-4-5`. Обе задаются в `.env`. Prompt caching не включён: сводок за сессию единицы, а общий префикс промпта (≈1,5 тыс. токенов) у трёх видов разный, выигрыш копеечный.
- **Новый текст всегда неопубликован.** Опубликовать игроку можно только вступление и сцену перехода; перед публикацией Jev проверяет выдумки относительно данных (`FACT_WARN = 0,6`) и утечку скрытых черт персонажа. Если Jev не ответил — мастер видит это и решает сам.
- **Ошибки Claude** (нет ключа, ключ не принят, лимит, таймаут, нет сети, отказ модели) возвращаются мастеру понятным текстом; сервер и игра продолжают работать.

## 2026-10-05, этапы 1б и 7

- **Службы — LaunchDaemon в `/Library/LaunchDaemons` с `UserName` владельца** (сервер, nginx, бэкапы, IP Cloudflare, DDNS, ротация логов). Стартуют без входа в систему. FileVault нужно выключить (docs/ops.md).
- **Перезапуск при выкладке без sudo:** `deploy.sh` шлёт серверу SIGTERM, launchd (KeepAlive) поднимает его из нового `current`. `launchctl kickstart` в системном домене требует root, поэтому не используется. sudo нужен только для установки служб и для `restore.sh`.
- **Релизы:** `deploy.sh` клонирует закоммиченный код из рабочего репозитория (`file://`), так что в прод попадает только то, что в git. Ссылка `current` меняется атомарно (`mv -h`), хранятся 3 релиза.
- **Защита origin:** `ssl_reject_handshake` для любого чужого имени, Authenticated Origin Pulls (глобальный CA Cloudflare; при желании позже — свой сертификат на зону), allow только IP Cloudflare, `real_ip_header CF-Connecting-IP`. Конфиг проверен `nginx -t` на nginx 1.29.5 с временным сертификатом.
- **Бэкапы:** `backup.mjs` — SQLite backup API, `integrity_check`, gzip, копия `data/media`; каждые 30 минут при игре за последние 3 часа и ежедневно в 04:00; 48 + 30 снимков; зеркало `BACKUP_MIRROR` необязательное, его ошибка не ломает основной снимок.
- **Логи:** копия с датой и обнуление на месте раз в сутки (launchd открывает логи с дозаписью, переоткрывать не нужно), архивы 14 дней. Без newsyslog и root.
- **Страница «Состояние»** у мастера в «Участниках»: версия, аптайм, память, размер базы и картинок, последний бэкап, `nginx -t` (если задан `NGINX_BIN`), дата списков Cloudflare, DDNS, наличие ключей.

## 2026-10-05, оформление и правки после первого запуска

- **Оформление в стиле Claude** (Anthropic brand guidelines): кремовый `#faf9f5` / почти чёрный `#141413`, оранжевый акцент `#d97757`, Poppins для интерфейса и заголовков, Lora для текста карточек, дневника, заметок и сводок. Тёмная тема — по системной настройке. Общий экран всегда тёмный. Иконка перекрашена. Шрифты — Google Fonts.
- **Socket.IO: отсутствие `Origin` разрешено.** Браузер не шлёт Origin в GET на свой же сайт, и первый запрос polling отклонялся — индикатор висел на «Переподключение». Межсайтовые запросы Origin несут всегда; вход всё равно по cookie.
- **Список входа по коду комнаты** показывает только тех, кто уже задал PIN или пароль.
- **`npm run setup` без терминала:** пароль мастера из `ZG_GM_PASSWORD`. Корневые `*:dev` скрипты передают аргументы дальше (`-- --name …`).
- Блок «Сводки» на странице персонажа свёрнут по умолчанию.

## 2026-10-05, этап 8

- **Дальнейшие этапы 8–11** (решение Рустема): сначала готовность к первой сессии, потом библиотека противников, дополнения карточки, удобства игрока. Снаряжение правят игрок и мастер, состояния и связи — только мастер. Уведомления — значки внутри приложения, без Web Push (новая зависимость, VAPID-ключи, свой service worker, на iOS только в установленном приложении 16.4+).
- **Заметки привязаны к сессии и на сохранении.** Клиент шлёт `sessionId`; если мастер в другой вкладке начал новую сессию, сервер отвечает 409 `session_changed`, и мастер сам решает, переносить ли текст. Без этого несохранённый текст старой сессии молча попадал бы в новую.
- **Суждения Jev о записи дневника стираются**, когда запись становится личной или удаляется (`forgetJudgments`). Фоновая проверка `diaryMatch` после ответа Jev перечитывает запись: если она стала личной, удалена или переписана, ответ выбрасывается. Раньше в этом окне мастеру уходила устаревшая копия текста записи, уже ставшей личной (нарушение правила 7 CLAUDE.md).
- **Вопрос с ответом мастера остаётся вопросом** при правке игроком: меняется только текст.

## 2026-10-05, этап 9

- **Противник сессии копируется из библиотеки** (имя и сила в строку `game_session`) плюс ссылка `opponent_npc_id`. Броски по-прежнему читают только строку сессии. Правка силы противника из библиотеки обновляет копию в сессии, удаление противника оставляет копию как ручной ввод.
- **Миграция 0005_npc поправлена руками:** drizzle-kit при `ADD COLUMN` с внешним ключом не пишет `ON DELETE SET NULL`, и удаление противника падало бы на внешнем ключе. В схеме Drizzle правило указано; при следующих `db:generate` это место проверять.
- **Конвейер картинок вынесен в `domain/media.ts`** (`storeImage`, `removeImage`, `mediaAllowed`, `mediaPath`). Стол получает портрет только показанного противника, как и картинку только показанной сцены.

## 2026-10-06, этап 17

- **Живая физика в браузере** (решение Рустема): Rapier (`@dimforge/rapier3d-compat`) в фоновом потоке; бросок просчитывается целиком сразу после нажатия, параллельно запросу к серверу. Траектория — 30 кадров/с, проигрывается с интерполяцией.
- **Посадка на число сервера через симметрию тела:** физика честная; если вверху выпала грань f, а сервер прислал значение на грани k, к повороту каждого кадра справа домножается поворот R из группы симметрий кубика (k → f, вершины → вершины). Форма в каждом кадре та же, столкновения те же, вверху — число сервера. Клиент ничего не решает: значение только из ответа сервера.

- **Физика вне предкэша PWA:** поток с WebAssembly весит ~4 МБ — грузится при первом открытии «Бросков», дальше из кэша (CacheFirst). Лоток (three + r3f) — ленивый чанк ~245 КБ gzip, в предкэше.
- **Один React:** three, r3f, motion, radix, sonner собираются Vite заранее (`optimizeDeps.include`, `resolve.dedupe`), иначе при первом открытии лотка r3f получал вторую копию React.

## 2026-10-06, этап 24: фигурки на карте

## 2026-10-06, этап 25: бой на столе

- **Когда бой.** Публичный бросок игрока, у персонажа есть фигурка, исход — не бросок удачи (то есть d10 против противника), а на столе показан противник, который одновременно противник сессии, и у него есть фигурка. Иначе — 3D-кубик, как раньше. Противник сессии раньше столу не сообщался; условие «показан на столе» значит, что мастер сам раскрыл его столу, — нового переключателя не нужно. В `TableNpc` добавлены `figure` и `opponent` (показанный — он же противник сессии); стол перечитывает состояние при смене противника сессии и новой сессии.
- **Фигурка бросающего** — в публичном событии броска (`RollPublic.figure`), на момент броска. Внешность, не секрет; уходит и в историю ленты (несколько сотен байт на бросок).
- **Исход показывает сервер**: сцена берёт `effect` броска и только рисует его — крит (крит. успех и крит. урон), попадание (успех, сильный успех, заметный урон), царапина, промах (провал, провал с осложнением).
- **Анимация** — те же `FigureSprite` и листы LPC, Motion для перемещений; сцена — свой ленивый чанк, фигурка противника подгружается заранее, как только он показан. Облегчённый режим и «Анимация выкл.» — без сцены. Страховка 9 с: очередь бросков не встаёт, даже если кадры не идут.

## 2026-10-06, этап 28: путь и время в дороге

- **Маршрут — общий код** (`shared/src/travel.ts`): Дейкстра по дорогам карты, концы дорог — места. Отряд в базе сразу в конце пути, путь — только анимация (4–12 с по длине), её играет клиент, увидевший новый номер похода; при открытии карты знамя просто стоит. Без часов сервера: рассинхрон времени не важен. Ручная перестановка («Партия») обнуляет поход.
- **Предложения** — таблица `map_proposal`: одно ожидающее на игрока и карту, видят мастер и сам игрок (событие `map:proposal.changed` — только ему). Принятое ведёт отряд и закрывает остальные ожидающие на этой карте. Jev не участвует: состояние меняет мастер.

## 2026-10-06, скорость карты на телефоне

- **Причина рывков на iPhone (16 Pro Max — не слабое устройство) — код.** Safari медленно растрирует большие SVG-фильтры (шум бумаги `feTurbulence`, размытие тумана 28, смещение заливок), а бесконечная анимация пульса отряда внутри SVG заставляла перерисовывать всю карту с фильтрами каждый кадр; после масштаба фильтры пересчитывались в масштабе × DPR 3.
- **Пульс и маркер отряда — HTML** над картой (анимируется только свой слой). Слои рисунка — `memo`; растр на время жеста (`will-change`) ставится прямо в DOM, жест не перерисовывает карту React.
- **Мягкие слои пергамента запекаются** (`maps/bake.ts`): бумага и зерно, светотень, тон земель, свечение границ, мглы, размытые леса, туман, штриховка, край — один раз в canvas 2400 px (телефон 2000, мало памяти — 1600) по ключу «карта + открытые регионы»; дальше картинка только двигается. Чёткое (реки, деревья, горы, дороги, границы) и подписи — живым SVG поверх (тексты — только там: в картинку внешние шрифты не грузятся). Открытие региона — плавная смена картинки вместо анимации маски. Не запеклось (или `?nobake=1`) — прежние живые фильтры. Леса теперь лежат под реками (были над ними) — разница едва заметна.
- **Телефон: карта на весь экран** (`data-map-full` на `<html>`, ставит экран игрока на вкладке «Карта» при пальце или узком окне): шапка скрыта, элементы карты поверх неё, навигация колонкой справа без «+»/«−»; в альбомной ориентации (высота до 520 px) вкладки — колонка слева. Компонент карты не пересоздаётся — меняется только раскладка (CSS). Карта на телефоне открывается заполняя экран. Заодно исправлено: вид камеры, заказанный до первого измерения окна (наезд на отряд), больше не теряется.
- **3D**: высоты, пятнистость, природа и облака-ориентиры — кэш на вкладку (переход мир ⇄ регион и «3D/Пергамент» без пересчёта); природа пересобирается только при смене раскладки мест. Экземпляры — по ячейкам 4×4 (отсечение невидимого вблизи), буферы моделей общие; мелочи — вблизи (масштаб ≥ 2,2); облака тумана — только над туманом; в движении чёткость 1, после остановки — полная; при долгих кадрах полная чёткость снижается шагами по 0,25 и запоминается (`zg:3d:dpr`); тени — только при сдвиге вида или сцены; стол — не чаще 30 кадров.
- **Модели** — сжатие meshopt (`EXT_meshopt_compression`, кодировщик `meshoptimizer` — dev-зависимость, распаковка — `MeshoptDecoder` из three): 1,8 МБ → 865 КБ. Шаблон nginx сжимает JSON, `.glb`, SVG.
- **Счётчик `?perf=1`** — для замеров Рустемом на телефоне до и после (кадры, худший кадр, в 3D — вызовы и треугольники, время сборки).

## 2026-10-08, этап 32: звук на столе

- **Звуки — Kenney (CC0):** Casino Audio 1.1 (кубик), Impact Sounds (стук, колокол, удары), RPG Audio (страница, дверь, клинок). Архивы с kenney.nl, sha256 проверяется в `tools/extract-audio`: адреса у Kenney содержат хэш и могут смениться — тогда скрипт остановится, адрес и sha256 обновляются вместе. Колокола «аккорда» в наборах нет: крит — тяжёлый колокол, провал — глухой мягкий удар.
- **Два формата:** `.m4a` (AAC 96 кбит/с моно, ffmpeg) — понимают Safari, браузеры телевизоров и Chrome; `.ogg` — запасной, если AAC нет. Выбор — `canPlayType`. 17 вариантов 9 звуков, ~170 КБ m4a; вне предкэша PWA, `CacheFirst` `zg-sfx`, версия в `?v=`.
- **Web Audio, не `<audio>`:** файлы декодируются при включении, звук стартует без задержки — стук попадает в удары кубика (`onImpact` той же физики, что вибрирует на телефоне; лёгкие касания и дробь чаще 90 мс — без звука). Не больше двух голосов: лишний стук пропускается, важный звук заменяет старый.
- **Только стол, по умолчанию выключен:** браузеры дают звук только после нажатия, а стол открывается сам. После перезагрузки — «Звук: нажмите», первое нажатие по экрану или кнопка пульта его возвращают (нажатие на саму кнопку звука решает она — иначе звук включился бы и тут же выключился). Телефоны игроков молчат: за столом звук из нескольких телефонов мешал бы.
- **nginx:** `location /sfx/` с типами `audio/ogg`, `audio/mp4` и `try_files =404` — без файла не отдаётся `index.html`.

## 2026-10-08, этап 33: существа LPC

- **Набор — «[LPC] Monsters»** с OpenGameArt (монстры базового LPC от Charles Sanchez / CharlesGabriel, летучая мышь — bagzie, атаки — bluecarrot16; CC-BY-SA 3.0 / GPL 3.0, мышь — ещё OGA-BY 3.0). Архив проверяется по sha256. Авторы — на экране «Авторы графики».
- **Отдельный скрипт** `tools/extract-lpc/creatures.mjs`, а не второй источник в `extract.mjs` (как было в плане): иначе ради существ пришлось бы заново клонировать и пересобирать детали людей ULPC — лишний риск изменить готовые листы.
- **Раскладка листов в наборе не описана**: ряды — как у LPC (вверх, влево, вниз, вправо), кадры по анимациям подобраны по самим листам (сначала движение базового набора, затем атака; «ранен» — кадр исчезновения у призрака, у остальных — один кадр стоя). Скрипт проверяет, что кадры не выходят за лист. Снаряд слизня отдельным листом не используется.
- **Без цвета** (в плане был `tint`): у существ нет палитр LPC, перекраска по оттенкам дала бы грязь. Нужен будет цвет — отдельным решением.
- **Схема**: `FigureSchema` — объединение `HumanFigureSchema` (как было) и `CreatureFigureSchema {v:1, creature}`, обе `strictObject`. Старые фигурки — люди, верны без миграции. Персонажам — только человек: `POST` фигурки игрока и мастера на персонажа проверяет `HumanFigureSchema`, игрок не пришлёт существо даже запросом в обход интерфейса.
- **Отрисовка**: `sheetOf` у существа вырезает кадры анимации в лист того же вида (`Sheet` + `first`, `fps`), поэтому `FigureSprite`, карты, город, отряд и бой на столе не менялись. Размер кадра свой (пчела 32, цветок 128) — существо на карте и в бою в естественном масштабе к людям. Кто бьёт издали (глаз, большой червь, тыквенный король) — `attackOf` даёт «заклинание», в бою на столе не подходит.

- **Модели — KayKit Character Pack: Adventurers 1.0 и Skeletons 1.0** (Kay Lousberg, CC0), закреплённые коммиты `672074b7` и `15b62b9b`. 9 моделей, у всех одна оснастка (41 кость).

- **Анимация — только в пути:** 3D-карта рисует кадры по необходимости; постоянная анимация «стоит» держала бы перерисовку всё время (батарея телефона). Стоя — поза первого кадра Idle. Модель смотрит по ходу движения.
- **Жетон тот же:** подставка, имя, выбор, перетаскивание и подписи — HTML поверх, как у фигурок; вместо спрайта — модель в сцене (`MapScene.addUnit`), положение — из того же жетона каждый кадр. Не загрузилась модель — фигурка или буква.
- **Видимость:** `model` в жетоне игрока и стола — только у видимых жетонов (`projectMapPublic`, `strictObject`); у персонажей всегда `null`.
- **Замеры** `?perf=1` на iPhone до и после — за Рустемом (T34.9).

## 2026-10-08, этап 35: активность игроков у мастера

- **Только в памяти сервера, журнал — 30 смен на игрока** (решение Рустема): это подсказка во время игры, а не протокол; таблица и миграция не нужны. После перезапуска пусто, игроки сообщают заново при переподключении.
- **Без набранного текста.** Действие — только перечисления и id (`PlayerActionSchema`, `strictObject`): подпись броска, текст записи, вещи, заметки и поиска не уходят. Название места мастер получает с сервера по id в своей комнате, чужой id отбрасывается.
- **Дневник — одно «пишет запись»**, без вида (дневник, вопрос, «Только мне») и без «новая / правка»: иначе мастер по активности узнал бы о записи «Только мне» (правило 7) — например, по правке записи, которой у него нет.
- **Только мастеру:** `gm:presence.changed` — через `publish(..., {kind:'gm'})`, список — `GET /api/gm/presence` с `requireGm`. В Jev и Claude не уходит.
- **Нагрузка:** клиент шлёт с задержкой 400 мс и только при изменении, `volatile` (без очереди при обрыве); после переподключения — заново. Сервер принимает не больше 120 событий в минуту на игрока, лишнее молча отбрасывает; формат — `safeParse`, от мастера и стола событие не принимается.
- **Несколько устройств:** показывается последнее видимое (не свёрнутое), иначе последнее; мастеру — их число.
- **Без дрожания журнала:** новый сокет ждёт первую активность до 1,5 с; «не в сети» — через 3 с после последнего сокета (перезагрузка страницы не даёт «вышел / вошёл»).
- **Подписи частей фигурки и вкладок игрока — в shared** (`FIGURE_SLOT_LABELS`, `PLAYER_TAB_LABELS`): страница мастера не тянет каталог LPC.

## 2026-10-09, этап 39: отряд разделяется

- **Запрос Рустема без подробностей** — решения ниже приняты по умолчанию; поменять — по слову.

- **В отряды входят только персонажи игроков** (с владельцем): персонаж без игрока не попадает ни в состав, ни в подписи — как и в фигурки отряда раньше.
- **Игрок видит все открытые отряды**, свой — отмечен (`mine`). Путь, дни, предложение и вход в город — только от своего: город открывается тем, чей отряд у стен. Игрок без персонажа — в основном.
- **Скрытый отряд не уходит никому**, в том числе своим игрокам (прежний смысл «маркер спрятан»): ни счётчика, ни следа. id отряда — nanoid, основной — `main`.
- **Сигнал «место изменилось»** сравнивает карточку, видимую при любом открытом отряде рядом: игроку другого отряда сигнал ничего не выдаёт — его отряд виден и так.
- **Предложение ведёт отряд автора**, принятое закрывает ожидающие только у этого отряда.
- **Соединить: отряд встаёт на место того, в который вливается**; основной остаётся основным (вливаясь, он переезжает в точку другого, а тот исчезает). Не больше 6 отрядов.

## 2026-10-09, этап 40: свои шрифты и лёгкие картинки

- **Шрифты — из сборки, не с Google Fonts.** 43 семейства тем, оболочек, наборов и карты плюс базовые Lora и Poppins берутся из пакетов `@fontsource/*` (шрифты OFL, пакеты MIT), подмножества cyrillic и latin. Причины: без сети оболочка и карта теряли шрифт; каждый игрок делал запросы к Google; `preconnect` к чужим хостам в `index.html`. Внешних запросов за шрифтами больше нет.
- **Один загрузчик** `web/src/lib/fonts.ts`: `ensureFont(family)` — динамический импорт CSS семейства (отдельный чанк Vite), один раз, отказ сети оформление не ломает. Движок тем (`cardTheme/index.ts`), наборы (`packs.ts`), оболочки (`shells.ts`, вместе со стилями) и карта (`maps/fonts.ts`) зовут его вместо `<link>` на Google. Веса — объединение того, что просили все места.
- **Предкэш PWA — только базовые шрифты** (Lora, Poppins, 11 файлов); остальные ~135 файлов woff2 (≈3 МБ) качаются при первом показе и дальше берутся из кэша `zg-fonts` (CacheFirst, до 200 файлов). Иначе установка тянула бы шрифты всех 46 тем.
- `fontsHref` и `PRELOADED_FONTS` в `engine.mjs` остались (копия движка артефакта), но не используются.
- **Картинки: превью и thumbhash рядом с полным файлом.** `storeImage` кладёт `<id>.webp` (до 1920 px) и `<id>.t.webp` (до 480 px) и пишет в строку `image_hash` (thumbhash, пакет `thumbhash`, MIT, ~28 байт base64). Игроку и столу уходит `{url, thumb, hash, w, h}` (`ImagePublicSchema`, strictObject) — превью и хэш только вместе с url, по тем же правилам видимости: `mediaAllowed` сводит `<id>.t.webp` к правилам своего полного файла. Хэш — цветовое пятно 100 px, текста и деталей не несёт.
- **Старые картинки досчитываются при запуске сервера** (`backfillMedia`, в фоне, по одной), а не лениво по запросу: проекции синхронные, sharp — нет. Пока превью нет, клиент (`components/Pic.tsx`) по 404 берёт полный файл. Отдельной команды `media:rebuild` нет — не понадобилась.
- **Сжатие перед загрузкой — в браузере мастера** (`browser-image-compression`, MIT): файлы больше 1,5 МБ уменьшаются до 2048 px и ~2 МБ; HEIC не трогается (сервер читает его сам). Предел 15 МБ на сервере остаётся.
- Стол (`TvScene`, `TvNpc`) по-прежнему показывает полный файл и ждёт `decode()`: ТВ в локальной сети, плейсхолдер там не нужен.

## 2026-10-09, этап 41: push-уведомления

- **Web Push через `web-push` (MIT), протокол VAPID.** Ключи — `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` в env, их делает `npm run vapid` (ничего не печатает, только дописывает). `VAPID_SUBJECT` — https-адрес (`PUBLIC_ORIGIN`), почта не используется. Без ключей всё выключено: `/api/push/key` → `{enabled: false}`, колокольчика в шапке нет.
- **Подписка = устройство** (`push_subscription`, endpoint уникален): игрок и мастер; стол — никогда. Подписки — внутренние данные сервера, наружу не уходят; при входе с подпиской клиент напоминает о ней серверу (`resync`), чтобы восстановление базы её не теряло.
- **Тело без свободного текста.** `PushNoteSchema` (strictObject: title, body, url, tag); в body — только имена мест и участников, которые адресат и так видит; ни текста ответа мастера, ни текста слуха. Единственное место отправки — `server/src/push/send.ts`, перед шифрованием — `.parse()` и `findGmLeak` (как в `publish()`). Push-службы Apple, Google и Mozilla получают тело зашифрованным, но правило действует всё равно: экран блокировки читают чужие глаза.
- **Что шлём.** Игроку: решение по его предложению (и авторам закрытых заодно), ответ мастера на запись, слух или задание, ставшее открытым в открытом месте, «Позвать за стол». Мастеру: новое предложение, новый вопрос (или переписанный открытый). Личные записи не порождают ничего. Остальные события (карточка, броски) — нет: во время игры все в приложении.
- **Не дублировать открытое приложение** — решает сервис-воркер: есть видимое окно — уведомление не показывается (сокет уже доставил). Серверу знать, кто онлайн, для этого не нужно; присутствие (этап 35) остаётся только мастерским.
- **Отказы:** 404/410 — подписка удаляется; иначе `fails + 1`, после 5 — удаляется. Отправка в фоне, ошибки игру не трогают.
- **Сервис-воркер по-прежнему `generateSW`**; `push` и `notificationclick` — в `web/public/push-sw.js` через `workbox.importScripts`. Нажатие: открытое окно получает `postMessage` с url и само переходит (у игрока — `?tab=`), иначе окно открывается.
- **Сервис-воркер включён и в dev** (`devOptions.enabled`): иначе push не проверить. Предкэша в dev нет, только правила runtimeCaching.
- **Значок на иконке** (Badging API) — число вкладок с непрочитанным из `lib/unread.ts`; считается на устройстве, сервер не участвует.
- «Позвать за стол» — не чаще раза в минуту на комнату (в памяти сервера).

- **Правка после доставки — только заметка мастера**: текст у игрока уже на руках, менять его задним числом нечестно. Удаление убирает письмо у игрока (сигнал `letters:removed`).

## 2026-10-09, этап 44: дела между сессиями

- **Одно дело на персонажа на сессию** (уникальный индекс сессия+персонаж); дело принадлежит активной сессии на момент выбора — «чем занят после этой игры». Игрок меняет его до разбора; после «Начать новую сессию» оно становится «прошлым» и ждёт разбора у мастера.
- **Срока нет**: до этапа 46 (расписание) дело живёт «до следующей сессии». Разбор — на игре или раньше, когда мастер захочет.
- **Вид и текст дела видит мастер** — это не личная запись дневника, в листе сказано «Мастер это увидит». Личные записи дневника в итог дела не попадают (Claude получает только вид, текст дела и открытое описание персонажа).
- **Итог пишет мастер**; черновик Claude — быстрая модель, Jev не участвует (оценка исхода — решение человека). Игроку уходит только итог после «Разобрать»; подсказка мастера Claude и черновик — нет. Повторный разбор переписывает итог без повторного push.
- Push игроку — «Итог дела» с подписью вида; мастеру при новом деле push не шлём: дела копятся до игры, достаточно карточки на «Игре».

## 2026-10-09, этап 45: слухи по расписанию и сказы игроков

- **Общий планировщик** `realtime/scheduler.ts` (тик 30 с, при запуске сразу) вместо отдельного у писем: доставляет письма (этап 42) и открывает слухи с `reveal_at`. Открытие по расписанию — тот же путь, что ручное: `visible`, `revealed_at`, push игрокам, сигнал карточки места. Ручное открытие снимает расписание.
- **«Первым услышал»** — отметка ставится, когда игрок внутри города открыл «Слухи и задания» и слух там был (клиент шлёт `heard` по каждому новому для него слуху один раз за сеанс). Хранится участник, наружу — имя персонажа (или участника). Отметка только у открытого слуха: следа скрытого нет.

Не больше трёх ожидающих на город от игрока. Сказ — всегда «слух»; «задание» из него делает мастер. Отклонённый удаляется.

## 2026-10-09, этап 48: искры

- **Журнал, не счётчик**: `spark` хранит ±1 с видом (`award`, `quiz`, `spend`) и причиной; баланс — сумма, не ниже нуля. Мастер видит журнал, игрок — только число (причины мастера — его дело).
- **Переброс — тот же `roll:request` с `rerollOf`**, а не отдельный маршрут: анимация лотка, дедупликация по `clientRequestId` (двойное нажатие не тратит две искры), доставка в ленту — всё как у обычного броска. Сервер берёт вид, видимость и подпись у исходного броска, проверяет: свой бросок игрока с персонажем, не старше 10 минут, ещё не перебросанный, искра есть. Трата пишется после вставки броска.
- **Прежний бросок остаётся в ленте**, новый помечен `reroll` у всех аудиторий: честность за столом важнее красоты.
- **Искра за викторину** — одна за главу при всех верных ответах (обещание этапа 43); начисляется в `answerQuiz`.
- Столу баланс не уходит; переброс стол видит как обычный бросок с пометкой.

## 2026-10-09, этап 49: знакомые

- **Знакомство пишет сервер при выдаче карточки места изнутри города** (`meetAt` в маршруте игрока): игрок увидел «Кто здесь» — встретил. Только открытые жители; скрытые знакомыми не становятся, следа нет. Без персонажа знакомых нет.
- **Заметка игрока о знакомом — только игроку**: мастеру не отдаётся (`GmAcquaintance` без заметки), в Jev и Claude не уходит — по правилу «только для меня». Отношение мастер видит: это игровой сигнал, не дневник.
- **Имя, фигурка и роль — вживую** из библиотеки и последней открытой записи «кто здесь»: переименование противника меняет знакомого у всех. Портрет противника игроку по-прежнему не уходит.
- Удаление противника убирает знакомства каскадом; удаление места оставляет знакомство без места встречи.

- **Чудище — противник с флагом `bestiary`**, а не отдельная сущность: у него уже есть имя, фигурка, модель и сила; добавлено только описание для игроков. Знакомые (этап 49) — люди из «Кто здесь», бестиарий — твари из боя; одно и то же существо может быть и там, и там.
- **Открытие — назначение противником сессии** (`setOpponent` с npcId) или кнопка мастера; одна запись `bestiary_unlock` на комнату и противника — коллекция общая на отряд. Скрыть обратно можно.
- **«Открыто N из M» выдаёт число закрытых чудищ** — осознанно: это коллекция, её смысл в полноте. Правило 6 — о скрытых чертах персонажа, не о монстрах; имена и всё остальное закрытых не уходят (силуэты без данных).
- Стол бестиарий не показывает; 3D-предпросмотр в приложении не делали (своего компонента нет), показана фигурка и название модели.
- **Справочник D&D SRD 5.1** (решение Рустема): `seed/bestiary-srd.json` из Open5e (`tools/extract-bestiary`), лицензия CC-BY-4.0 — attribution в файле, в «Авторах графики» и у кнопки. Берём только статблок (имя, вид, CR, КД, хиты, характеристики, особенности, действия коротко) — в SRD нет художественных описаний, их пишет Claude по статблоку. Сила по CR — таблица `powerFromCr` (CR 1 → 20, CR 5 → 55, CR 10 → 95, CR 20 → 300, CR 30 → 1000) под ступени силы «Зеленогорья». Имя остаётся английским: переводить 322 имени автоматически — плодить ошибки, мастер переименует нужные.
- **Оформление бестиария по темам** (решение Рустема): базовые правила на `--ct-*` в `app-skin.css`, манера — в CSS оболочек (книга, летопись, терминал, КПК, пиксель, манга, комикс, досье); остальные оболочки берут базу.

## 2026-10-09, этап 51: открываемые оболочки

- **Свободны «Книга» и оболочка темы персонажа**; остальные 14 открываются. Открытие выбирает игрок — так награда ощущается своей, а мастеру не нужно угадывать вкусы.
- **Заработанное не хранится, а считается** из уже имеющихся данных (`domain/shells.ts`): моменты персонажа / 2, викторины без ошибок, чудища бестиария отряда / 3, завершённые сессии комнаты / 3, плюс подарки мастера. Хранятся только выборы и подарки (`shell_unlock`). Отменить веху задним числом (удалить момент) может уменьшить «доступно», но уже открытое не закрывается.
- **Проверка «свободная ли оболочка» — на клиенте**: тема персонажа считается движком тем в браузере, сервер её как оболочку не знает. Сервер проверяет, что оболочка из списка, не открыта и есть доступное открытие. Оформление — косметика на устройстве игрока, мастера и стол не касается, поэтому клиентской проверки достаточно.
- **Ранее выбранная тема закрытой оболочки не применяется** (`themeAllowed`): до этапа 51 игрок мог выбрать любую тему; теперь — тема персонажа, пока оболочка не открыта.
- Push не шлём: на кнопке «Оформление» — пометка «можно открыть оболочку». `SHELLS` и подписи переехали в `shared/src/shells.ts`.

## 2026-10-09, этап 52: отклики на стол

- **Перечень вместо текста**: четыре отклика с фиксированными подписями — игрок не пишет ничего, что могло бы оказаться на общем экране без мастера.
- **Только через сокет и только столу** (`table:reaction`, `publish` с аудиторией `table`): нигде не хранится, в ленту и мастеру не уходит. Имя — персонажа (или участника без персонажа).
- **Лимит 6 за 10 секунд на игрока**, лишние молча отбрасываются; отправка `volatile` — без связи отклик просто теряется.

## 2026-10-09, этап 53: фото сессии в летописи

- **Фото — строки `chapter_photo` по общему конвейеру картинок** (этап 40: WebP до 1920 px, превью, thumbhash, сжатие в браузере). До 24 на главу; удаление фото или главы удаляет файлы.
- **Видимость фото = видимость главы**: `mediaAllowed` пускает игрока к файлу и превью только опубликованной главы своей комнаты; мастеру — всегда; столу — нет. Черновик главы с фото игрокам не выдаёт ни фото, ни их числа.
- «Альбом» — сбор фото опубликованных глав на клиенте (до 48 последних), отдельной таблицы нет. Push отдельно не шлём: фото приходят с главой.
- Согласие людей на снимках — договорённость за столом; руководство напоминает мастеру спросить.

## 2026-10-09, этап 54: поиск мастера

- **FTS5 в той же SQLite**, таблица `search_doc` создаётся при запуске (`CREATE VIRTUAL TABLE IF NOT EXISTS`), не через Drizzle: это индекс, а не данные; бэкап его несёт, но потеря не страшна.
- **Пересборка по подписи комнаты** вместо триггеров: перед поиском — по каждому источнику `count(*)` и максимум времени правки; изменилось — комната пересобирается целиком в транзакции. Для кампании в сотни строк — миллисекунды; триггеры на 12 таблиц и JSON персонажа были бы хрупче. Подпись — в памяти процесса; после перезапуска первая выдача пересоберёт индекс.
- **Токенайзер `unicode61 remove_diacritics 2`**: регистр, «ё/е» и диакритика не мешают; морфологии нет — запрос префиксный по каждому слову (`"слово"*`, AND). Спецсимволы FTS из ввода выбрасываются.
- **Не индексируются**: записи «только для меня» (правило 7) и заметки игроков о знакомых (этап 49). Ответ — только мастеру (`requireGm`); предохранитель onSend для мастера, как и раньше, не срабатывает.

## 2026-10-09, этап 55: QR-приглашение и анкета персонажа

- **Зависимость `qrcode` (MIT) в web**, грузится отдельным чанком только у мастера при показе приглашения. QR рисуется в браузере в SVG — ссылка никуда не уходит. На общий экран QR не выводится: приглашение одноразовое и на одного человека.
- **Анкета — таблица `questionnaire`** (одна на участника, ответы JSON по `QuestionnaireAnswersSchema`): видят игрок (свою) и мастер; в Jev и Claude не уходит; столу и другим игрокам — нет. Править можно, пока персонаж не выдан (сервер проверяет). Поле «чего не хочется видеть в игре» — инструмент безопасности, видит только мастер.
- **Жанры и вселенные для анкеты** игрок получает вместе с анкетой — это справочник рандомизатора, не тайна. Сервер принимает только ключи из справочника.
- **«Заполнить форму по анкете»** подставляет в форму рандомизатора имя, местоимение, жанр, вселенную и владельца; бросок и сохранение — по-прежнему руками мастера.

## 2026-10-09, этап 56: диктовка и экспорт

- **Диктовка — Web Speech API браузера** (без зависимостей). Распознавание делает не устройство, а сервис браузера: Chrome отправляет звук Google, Safari — Apple. Поэтому **для записей «Только мне» кнопки нет** — правило 7 говорит о Jev и Claude, но по смыслу личное не должно уходить и третьим сервисам. У кнопки подсказка, кто распознаёт.
- **Экспорт — целиком на устройстве игрока**: данные те же, что игрок и так получает (карточка, свой дневник с личными записями, письма); сервер ничего нового не отдаёт. Markdown — файлом, PDF — через окно печати браузера (`@react-pdf/renderer` не берём: ~1 МБ ради того, что умеет печать). Окно печати открывается синхронно по нажатию, иначе блокировщик всплывающих окон его гасит.
- Текст в окне печати экранируется перед разметкой — запись дневника не может вставить свой HTML.
